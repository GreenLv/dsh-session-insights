## Recovery classification contract

Both production analyzers (Node `plugin/lib/analyzer.js`, Python
`src/dsh_session_insights/analyzer.py`) implement the same rule. A tool result
whose structured `data.error.code` is exactly `TOOL_OUTCOME_UNKNOWN` or
`TOOL_NOT_STARTED`, with a valid non-empty call identity, is a recovery
result. It increments `tool_recovery: {outcome_unknown, not_started}` on the
session and in report totals and is never counted as a tool failure, a failed
verification, a permission block or a state change; it produces no retry
evidence. Recovery settles by the official `(callId, turn, step)` identity, so
a call settled by an ordinary result keeps its recorded outcome and a late
recovery result for that scope is ignored, while the same id in a later turn
is a distinct pending request counted once. Results that only mention a code
in text, or that carry an error object without these codes, follow the
ordinary result rules. Invalid V4 stays rejected, and a second result for an
already-settled call is rejected by the official strict catalog
(`settled call result repeat` negative case). The report schema declares
`tool_recovery` for totals and session summaries
(`docs/schema/report-v1.schema.json`).

acceptance. If those remaining host gates are required for release, they need
the user's Windows thread with a real profile-equivalent host, as in earlier
versions.
